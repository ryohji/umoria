# model/player の設計資料

model/player の 6 つの module（player_identity・player_progress・player_stats・
player_skills・player_spells・player_condition）について、ヘッダには書かない詳しい
設計の理由・不変条件・値の範囲をまとめる。宣言の約束はヘッダを見る。

## player_identity

### モジュール分割の判断

6つの答え（名前、性別、年齢、身長、社会階級、生い立ち4行）を1つのモジュールにまとめた理由：

1. 分割の通常ルール「一方を読まずにもう一方だけ読むか」では6つとも別モジュールになる
   - 6つとも別々に読まれる
   - どれも2つを足したり比較したりする処理は無い
2. しかし次の2つの理由で統合した：
   - 作成時に一度だけ設定され、その後は変更されない（名前のみ`change_name()`で再設定可能）
   - 同じ4箇所（キャラクターシート、ダンプ、save、墓）から読まれる

### 生い立ちのサイズ定数

- `PLAYER_HISTORY_LINES`: 4行（`get_history()`が4行で処理し、背景表の33万984通りの物語で5行目を必要としない）
- `PLAYER_HISTORY_LINE_SIZE`: 61文字（終端含む）。`get_history()`が60字で折り返し、8,057通りの物語が実際に60字ぴったりの行を持つ
- 名前の幅は`types.h`の`PLAYER_NAME_SIZE`に残す（ハイスコア表の名前フィールドも同じ幅で、それはこの問いではない）

### 名前が const char * を返す理由

4箇所がアドレスを通して書き込む（`get_string()`, `user_name()`, `rd_string()`など）。書き込み可能な`char *`を返すと窓口が無意味になる。各箇所はローカルバッファを用意し、完成した名前を`player_name_set()`に渡す。

### 性別が bool の理由

9つの呼び手が数値として使わず（3つが`? :`、6つが`if`）、すべて真偽として扱う。手編集されたsaveファイルの2は1として戻るが、ゲーム内で区別できない。

### 性別に付随する3つのルール（呼び手に残す）

1. 王 or 女王（`status_line.c`の`title_string()`, `death.c`の`tomb`と`kingly()`）
2. 新キャラの財布（`create.c`の`get_money()`: 社会階級×6 + 女性なら50）
3. 身長表の選択（`create.c`の`get_ahw()`: m_b_ht/m_m_ht or f_b_ht/f_m_ht）

### player_history_clear() の設計

4行を1回の呼び出しで空にする（フィールドはループが必要だった）。

### player_race と player_class の扱い

- 両方とも行番号（race[]とclass[]への添字）
- 数量ではない：算術は行の検索だけ、`_adjust`窓口は存在せず今後も無い
- 作成時と保存ファイル読み込み時の2回だけ書き込まれる
- width は byte のまま：256は0に、-1は255になる（範囲チェックしない：findings.md 24）

### race と class の名前の衝突

- `race`: 定数表race[]、owner_race、race_type.trace、high_scores.race は4つの異なるもの
- `class`: grep で69行見つかるが22行だけがこの表。35行は散文、3行は別の添字、8行はhigh_scores.class

### player_class_spell_type() が値を返す理由

NONE, MAGE, PRIEST の3値を返す。`player_class_casts_spells()`と`player_class_says_prayers()`の2つの述語に分けると：
- 11箇所では読みやすくなる
- しかし4箇所が3つすべてで分岐し、2つの述語では2回問い合わせて矛盾する可能性がある
- 3つの答えは1つの数（findings.md 43）

### player_class_spell_type() を呼ぶだけの2つの呼び手

`gain_level()`（level_ops.c）と`lose_exp()`（spells.c）はこの窓口だけを読む（各2回）。

### class_level_adj の重複（findings.md 42）

16箇所が`class_level_adj[row][column]`を読み、そのうち9箇所がコピー：
- 4箇所が disarming の合計を計算
- 5箇所が saving throw と device chance を計算
これらを畳むには`player_disarm.c`が`player_class.c`を呼ぶ形になる。

### 内部データ構造の選択

6つの答えは6つのstaticで、1つのstructではない。同時に設定されるが、2つ一緒に読まれることは無い。

### 性別の保存

store は bool だが、save file は依然として byte を読み書き：
- `rd_byte()`は`raw != 0`を`player_set_male()`に渡す
- `wr_byte()`は1または0を書き戻す

### 名前と生い立ちのゼロ埋め

`player_name_set()`と`player_history_line_set()`は store を先に空にする。`strncpy()`自体が境界までパディングするので、この行が追加で触るのは最後の1 byteだけ（PLAYER_NAME_SIZE-1 または PLAYER_HISTORY_LINE_SIZE-1 文字の名前/行の場合）。しかし約束「終端の後のすべてのbyteはゼロ」が store の履歴に依存しないようにするため残す。

### player_history_line_set() の設計

行は文字列として到着し文字列として保持される。60字の行の61番目のbyteに終端を1 byte 過ぎて書き込んだ2段階書き込みは消えた（bug candidate B21、何にも届かなかった。注記はtypes.hに）。

### player_race_name() と player_class_title() が届く先

race[] と class[] の read-only 定数表（externs.h で宣言）。なぜ名前だけがここにあり、行の残りは無いか：呼び手が欲しいのは種族/職業の名前。race[]を読む他の読み手が欲しいのは種族の統計（年齢の広がり、身長、選択可能な職業）で、それは別の問いで create.c に残る。

### player_race_name() の呼び出し数

呼び出し数を減らすものではない。3箇所それぞれが依然として1回ずつ呼ぶ。利益は、3箇所のどれも添字を綴らないこと。

### player_class の呼び出し数

33の呼び手、すべてが添字または byte をそのまま渡す：
- `class_level_adj[row][column]` 16回（to-hit 7回、disarming 4回、device 3回、saving 2回）
- `magic_spell[row - 1][spell]` 10回
- `class[row]` 3回（作成時の全行、first_spell_lev 2回）
- `player_title[row][level - 1]` 1回、`player_init[row][i]` 1回
- ハイスコアエントリと保存ファイル各1回

### 魔法学派の決定が呼び手に残すもの

- どの能力値に紐づくか（A_INT or A_WIS）
- どの語を印刷するか（"spell" or "prayer"）
- spell_names[]のどちらの半分に添字するか（SPELL_OFFSET or PRAYER_OFFSET）
- どの本を読めるか、本が全く必要か（priest は神から祈りを得て盲目でも学べる）

学派はクラスについての事実。それから従うものは spell code の仕事。

## player_progress

### player_level と player_experience の関係

level は保存されるが、experience によって固定される：

```
advance_price(level) = player_exp[level - 1] * expfact / 100
lev = experience が advance price を超えない最小の level
```

表のエントリはレベルを「去る」価格（到達する価格ではない）。すべての呼び出し箇所が添字する前に level から1を引き、キャラクターシートは「Exp to Adv.」として印刷する。

### 2つの約束の守りかた

約束は2つの異なる方法で守られ、両者を一致させるものは無かった：

1. `prt_experience()`（level_ops.c）：1レベルずつ登る。各ステップで`gain_level()`を呼ぶ
2. `lose_exp()`（spells.c）：底から数え直す。表を最初のエントリから歩き、価格が高すぎるまで進む

価格自体は5箇所で書き出され（misc3.c 3回、files.c と spells.c 各1回）、spells.c のコピーは添字を異なる端から始める。この約束がこのモジュールの目的：価格は1箇所で計算され（player_experience_to_advance_from）、登りは1つの問い（player_deserves_next_level）を尋ね、数え直しは1つの窓口（player_recompute_level）。2つの経路、同じ約束、同じ算術を通る。

### level が保存される理由

事故ではなく、このモジュールは純粋な結論に変えようとしない：wizard の「never die」トリック（death.c）は意図的に level に MAX_PLAYER_LEVEL を足し experience に5百万を足し、約束を何かが数え直すまで壊す。これが底辺の setter が存在する理由で、wizard コマンドがそれを使う理由：素の setter はコードが「これは意図的に experience が deserves する level ではない」と言う方法。

### experience fraction の用途

mana と hit points が保持する fraction とは異なる。それらは65536分の1での最大値の share で、regeneration によって返される。これは除算の余りで、除数は現在の level：モンスターを倒すと mexp × そのレベル の経験値で、キャラクターの進行度で分割される。割り切れない部分は65536分の1で保持され、積み上がって1ポイントになる。1つの呼び手が書き込み（monster_damage.c の mon_take_hit）、1つが読む（save file）。mana と hit points の窓口はここにコピーできない。

### 5つのルール

1. レベルを去る価格（player_experience_to_advance_from）：5つの呼び出し箇所が共有した式の1つのコピー
2. experience が丸ごと到着（player_gain_experience）と experience が share として到着（player_gain_shared_experience：上記の fixed-point 余り）
3. experience が去る（player_lose_experience）：nothing で止まり、決してその下に行かない
4. level と experience の間の約束、両端から（player_deserves_next_level：登り用、player_recompute_level：数え直し用、player_trim_surplus_experience：level 獲得時に捨てる余剰の半分）
5. ハイウォーターマーク（player_record_max_experience と player_restore_experience）：これまでに保持した最大の experience で、restore-level が戻すもので drain-life が奪えないもの

### ルールが意図的にしないこと

- 登ること。`player_deserves_next_level()`は問いに答える。再度尋ねるループは`prt_experience()`に属する。各ステップが「Welcome to level n」を印刷し、hit points・spells・mana を再計算し、level と title を再描画する。どれも数についての問いではない
- 新しい level の価値（hit-point 表、spell 数、mana）：他の問い、他のモジュール
- 印刷。`prt_level()`, `prt_title()`, `prt_experience()`自身の描画は呼び手に残る
- experience の出所：モンスター、罠、ポーション、初回詠唱、アイテム識別はすべて自分の量を算出して数を渡す

### player_experience_factor の範囲

100以上（これが数え直しが表の終端を越えて歩かない唯一の理由）。最も高価なキャラクターは165%（種族ベース100/110/120/125 + クラスシェア0/20/30/35/40）を支払う。10000000 × 165 = 1.65e9 で、符号付き32ビット数に収まる。約214を超える factor は最後の数レベルを負にし、キャラクターは永遠に登る。

### player_level_deserved_by_experience() が表を越えない理由

歩行は停止する。なぜなら表の最後のエントリ（1千万）は experience の上限（MAX_EXP、1千万より1少ない）より100以上のすべての factor で高価だから。これがこれが表の終端を越えて読まない全理由。どこにもチェックされていない。元のコードでも。何も変更しない。代わりに書き留める。

### player_hit_die の読み手

5つの呼び手、すべて create.c の hit point ローリング：レベル1の hit points、合計の2つの境界、表のレベル1行、レベルごとの`randint()`。ゲームプレイ中は誰も読まない。

### player_hit_die の設計判断

2つのテーブルがそれを決定し、両方ともキャラクター作成時で、その後は決して変わらない：
- 種族がベースを与える（race_type.bhitdie）：Halfling 6, Gnome 7, Elf 8, Half-Elf 9, Dwarf 9, Human 10, Half-Orc 10, Half-Troll 12
- クラスがそれに加える（class_type.adj_hd）：Mage 0, Priest 2, Ranger 4, Rogue 6, Paladin 6, Warrior 9

数は6（Halfling Mage）から21（Half-Troll Warrior）の間に収まる。create.c が hit point 表をローリングした後、ゲームの残りでは何も動かさない。

### player_hit_die_adjust の設計

クラスの調整、1つの呼び手（create.c）、種族のベースが配置された直後に適用される。store が1回だけ触られるよう、自身の窓口。負を拒否しない：class table のすべての adj_hd はゼロ以上。

### player_hit_die が問いである理由

記憶と単なる記憶。しかし save file が必要とする byte というだけではない（findings.md 37）。ここで2つのテーブルがそれを決定し、全 hit point 表がそれから構築される。

### hp_table の設計

1レベルごとに1回ロールされ、二度と変わらない。level を得ても新しい hit points をロールしない。以前に誕生時に決定された数を読む。エントリは累積：level 1 は hit die を保持し、各後続 level はその level のロールに前の合計を加えたものを保持する。したがって最上位 level の値はキャラクターの全生涯の hit points で、作成がその境界に対してチェックするもの。

### hp_table_slots() の使用制限

save file のみ。save file は1回の呼び出しで MAX_PLAYER_LEVEL エントリすべてを読み書きする（rd_shorts / wr_shorts）ので、値ではなくアドレスが必要。`death_cause()`がポインタを返すのと同じ理由。他は使うべきでない。

### player_hp の負の値

死んだキャラクターのマーク。唯一のマークはこれだけ：何も hit points をゼロでクランプしないので、致命的な一撃は負のままにし、save file を通してずっと負のまま。4箇所がマークを読む：

1. `take_hit()`はダメージを引いてすぐ問う（player_damage.c）
2. app/main.c はロード後に問う（キャラクターはシグナルやハングアップで死んで保存でき、戻る際に再び死亡マークを付ける必要がある）
3. save.c は「killed by」行を「(alive and well)」で上書きするかどうか決める
4. save.c は wizard resurrection で再び問い、数をゼロに戻す唯一の場所

数をゼロに整えた窓口は静かに4つすべてを壊す。これが`player_take_hp_damage()`が bool を返す理由で、`player_hp_marks_death()`が全く存在する理由：呼び手は名前を持つ問いを尋ねるべきで、数をゼロと比較するべきではない。

### player_hp の regeneration ルール

fixed-point 合計、maximum が大きすぎて short が wrap する場合のガード、トップでの停止（fraction をクリア「equal でも frac をゼロにセットしなければならない」）。

### player_take_hp_damage の設計

引き算して fatal だったかを報告。クランプしない：致命的な傷は意図的に数を負のままにする。なぜならそれが死のマークだから。呼び手が死ぬことが何を含むか決定。

### player_heal_hp の設計

治癒、トップでキャップ、何か起きたかを言う。既にトップにいるキャラクターは全く治癒されず、呼び手はそれを使って静かにする。fraction は部分的な治癒を生き延び、トップに達したときにクリアされる。

### player_change_max_hp の mana との違い

mana と異なり、ゼロの maximum は「全く何もしない」を意味する。「満タンで始める」ではない：mhp はキャラクターがまだ作られている間だけゼロで、`calc_hitpoints()`は意図的にその時新しい maximum さえ保存しない（create.c が両方を瞬時に埋める）。これが mana の窓口が単純にコピーできない最初の場所。

### player_gain/lose_temporary_max_hp の用途

Heroism（10ポイント）と super heroism（20ポイント）が同じ4行をそれぞれ書いた（app/dungeon.c）。登場：両方の数が一緒に上がるので、トップからの距離は変わらない。消失：maximum が先に下がり、残りがそれにキャップされる。キャップが噛んだかを言う（噛んだ時だけ呼び手が再描画）。

### player_resurrect_hp の使用

wizard resurrection のみの呼び手。死のマークが消される唯一の場所。

### player_mana の fraction の理由

このモジュールがルールを持つ理由。Regeneration は各ターン微量を返す：全 maximum に数百の65536分の1の factor（PLAYER_REGEN_NORMAL は197）を乗じ、PLAYER_REGEN_MNBASE の floor を加える。10 mana のキャラクターでこれは1ターンあたり100分の1ポイント未満なので、余りを保持する場所が無ければ何も戻らない。fraction はその余り：整数部分は残りに行き、下位16ビットが運ばれ、carry が満ちたとき更に1ポイントになる。外部の誰も見たがらない（save file だけ見る。なぜならリカバリ中に置かれたキャラクターは進行を失うべきでないから）ので、それに触れる算術はここに属する。

### player_mana の3つのルール（すべて fraction についてのルール）

1. regeneration（player_regenerate_mana）：上記の fixed-point 合計 + maximum が大きすぎて short が wrap する場合のガード + トップでの停止（fraction をクリア「equal でも frac をゼロにセットしなければならない」）
2. 支出（player_spend_mana）：満額支払えないときだけ fraction を空にする。通常の詠唱はコストを差し引いて fraction を alone のままにするので、次のポイントへの進行は支出を生き延びる
3. 新しい maximum（player_change_max_mana）：残りを比例して運ぶ、fraction を含む。古い maximum と新しいものはめったに whole multiple apart ではないから

### player_mana のルールが意図的にしないこと

- regeneration がどれだけ速く実行されるかは呼び手の数（hunger、resting、regeneration flag がすべてそれを動かす：app/dungeon.c）
- 詠唱が支払えないとき何が起きるか：気絶、ポイントごとに5ターン続く麻痺、constitution を傷つける3分の1の確率（magic.c, prayer.c）
- maximum がどうあるべきか：stat、class、level から算出（spellbook.c の calc_mana）。その後 PY_MANA を上げるのは status flags に属し、別の問い
- 印刷。`prt_cmana()`は store の内部から呼べないので、呼び手が自分で変更を見る（player_display_numbers.c が PY_ARMOR で持つのと同じ配置）

### player_spend_mana の戻り値

魔法のコストと実際に支出された額を言う：足りれば全コスト、足りなければそれより少ない。足りなくなると store を空にする（fraction も一緒）、負にはならない。呼び手が不足の cost を決定し、戻り値から判断できる。

### player_restore_mana の設計

store をトップまで満たし、それが何かを変えたかを言う：既に満タンのキャラクターへの restore mana のポーションは何もせず、それによって識別さえされない。

### player_change_max_mana の初回

maximum が無かったキャラクターは満タンで始まる（mana が全くなかったキャラクターは満タンで始まる）。

### player_lose_all_mana の用途

最後の spell を忘れる。支出ではない。

### player_gold の設計

記憶と単なる記憶。窓口はクランプしない、負を拒否しない、overflow を防がない。なぜなら元のコードがそれらのどれもここでしなかったから。ここでそれらをすることは振る舞いを保存するのではなく変更する。財布についてのすべてのルールは正確に1つの読み手を持ち、それに残る：

- 店は買えない購入を拒否（store_ui.c が先に尋ねる）
- 泥棒は10分の1を取り、持っているより多くを取れない（monster_melee.c が先に比較）
- 新キャラクターは少なくとも80 gold を与えられる（create.c）
- wizard コマンドは負を拒否（wizard.c）

### player_max_depth の設計

どこまで深く行ったか。現在の深度ではない（dungeon_level()、dungeon_level.h）。それは階段を使うたびに変わり、上にも下にも行く。この数は決して減らない。単位は dungeon levels、深度と同じ。町はレベル0。ゼロは「町より下に行ったことが無い」を意味し、すべてのキャラクターが始まる場所。

### player_max_depth がキャラクターの身体やスキルについてではない理由

キャラクターがいた場所の記録。3つの異なるファイルが3つの無関係な理由でそれを尋ね（スコア、word-of-recall の巻物、保存ファイル）、1箇所だけが答える。

### player_note_depth_reached の設計

このレベルに達したことを記憶する。2つのうち深い方を保持：比較はここにある。なぜなら1つの呼び手がいて、理由をこのモジュールの語で言え、このnumberに対する`>`は外に残らないから。したがって階段を上って戻ることは記録を下げられない。これが問いの意味。

### player_max_depth_set の用途

保存ファイルのみ。`hp_table_slots()`と同じ：ロードは書かれた数を復元しなければならず、マージではない。プレイはこれを使わない可能性がある：上の窓口がキャラクターがより深く到達したことを記録する唯一の方法で、後戻りできない。

## player_stats

### 概要

プレイヤーの能力値・ボーナス・AC・装備による特殊能力を管理する。7つのstat-to-bonusテーブル、4つの能力値（max/cur/mod/use）、17の特殊能力フラグ、AC・命中・ダメージなどの戦闘数値を保持する。

### Stat-to-Bonus テーブル (7種)

すべてのテーブルは `player_stat_use()` を読む。`stat_adj()` のみ引数でstatを指定。

- **stat_adj**: wisdom/intelligence用。唯一フロアが0（負にならない）
- **chr_adj**: charismaによる価格調整（パーセント）。3未満はすべて100%
- **con_adj**: HP補正。7未満は負、17以上は正
- **tohit_adj**: 命中補正。dexterityとstrengthを独立に計算して合算。上限がずれている（dex: 118, str: 117）
- **toac_adj**: AC補正。dexterityのみ
- **todis_adj**: 罠解除補正。2→4、6→8のようにギャップがある
- **todam_adj**: ダメージ補正。strengthのみ

### 4つのStat値

セーブファイルは max/cur/mod/use の順で各6個ずつ書く。

- **max**: restore時に戻る値
- **cur**: 現在の自然値
- **mod**: 装備による修正（int16_t、負あり）
- **use**: 実際に使う値（cur + mod、0-118にクランプされる）

### 17の特殊能力

**これらは記憶されない — 装備から毎回導出される。** `calc_bonuses()` が毎回ゼロクリアし、装備を歩いて再計算する。セーブファイルに残っているのは、ロード時に `calc_bonuses()` が呼ばれないからのみ。

#### 分類

1. **キャラクターに対して無効なもの（7種、ウィンドウ2つ）**
   - `free_act`: 麻痺無効（17種の中で最も参照が多い：11箇所）
   - 6つのsustain stat: stat drain無効。各statごとに1つ

2. **ダメージ無効化（5種）**
   - fire, cold, acid, light, falling damage

3. **身体の特殊な働き（4種）**
   - see invisible, regenerate, slow digestion, random teleport

4. **モンスターが気づくもの（1種）**
   - aggravation

#### 実装の要点

- **装備を歩かない。** `player_bonuses.c` がフラグを集めて渡す。identification・curseの判定はそちら
- **消化を管理しない。** `calc_bonuses()` がクリア前に古い値の効果を取り消し、最後に新しい値の効果を適用する。クリアと導出が2つのウィンドウに分かれているのはこのため
- **なぜを知らない。** 通知もロールもしない

#### See Invisibleの特殊性

2つのソースから付与される：
1. 装備（TR_SEE_INVIS）
2. timed "detect invisible" potion

このため専用の付与ウィンドウ `player_grant_see_invisible()` がある。

#### Sustainの2つの順序

ゲームは `A_STR, A_INT, A_WIS, A_DEX, A_CON, A_CHR` でstatを番号付けする。アイテムのp1は `1=STR, 2=INT, 3=WIS, 4=CON, 5=DEX, 6=CHR` と **4番目と5番目が逆**。2つのテーブルを使って変換する。

#### セーブファイル順序

17バイトが固定順で並ぶ。順序＝ファイル形式なので変更不可：
1. SEE_INVISIBLE
2. TELEPORT_AT_RANDOM
3. NEVER_PARALYZED
4. SLOW_DIGESTION
5. AGGRAVATE
6. RESIST_FIRE
7. RESIST_COLD
8. RESIST_ACID
9. REGENERATE
10. RESIST_LIGHT
11. NO_FALLING_DAMAGE
12. SUSTAIN_STR
13. SUSTAIN_INT
14. SUSTAIN_WIS
15. SUSTAIN_CON
16. SUSTAIN_DEX
17. SUSTAIN_CHR

### confuse_monsterとnew_spellsがここにない理由

- **confuse_monster** (glowing hands): 使い切りチャージ。スクロールがセットし、次の攻撃でクリア。装備からは付与されず、`calc_bonuses()` も触らない。timed state側
- **new_spells**: カウント（能力ではない）。学習可能な呪文数。study要求・spells_known.cと対をなし、専用モジュール（player_spells_to_learn.h）がある

### Weapon Too Heavy

使用中のstrengthで扱えない重さの武器を装備しているかどうか（`use_stat[A_STR] * 15 < weight`）。

- Trueの間、キャラクターシートの命中にペナルティ（`player_bonuses.c`）、掘削が困難（`terrain_commands.c`）
- 別の武器を装備するとクリアされる（`inven_menu.c` 2箇所）
- **セーブファイルには含まれない**（ロード時にクリア）

### Pack Speed Penalty

現在の荷物によるspeedペナルティのステップ数（0 = ペナルティなし）。

重量が限界を超えた分 ÷ 限界 で計算。非常に重い荷物は複数ステップのペナルティ。

読み取りは2つの質問に使われる：
1. 「ペナルティが変わったか？」（新しい計算値と比較、`check_strength`, `inven_check_weight`）
2. 「戻すべきspeedはいくつか？」（`save.c` がファイル書き込み前にマイナスを適用し、アンエンカンバーされた値を保存）

### Body Weight

キャラクターの体重（ポンド単位）。**10分の1ポンド単位ではない**。男性ハーフリングで約60、男性ヒューマンで約180（`src/model/data/player.c` の race[] の m_b_wt / f_b_wt カラム）。

#### 虚栄心ではなく物理量

キャラクターシートに表示されるが、8つのリーダーのうち4つはルール用：
- 持ち運べる重量（`inven_ops.c` の `weight_limit()`）
- 盾による bash のダメージ（`player_melee.c` の `py_bash()`、2回）
- ドア bash の成功率（`terrain_commands.c` の `bash()`）

#### 一度だけ書き込まれる

通常のキャラクターの人生で一度だけ書き込まれる：作成時（`create.c`、性別ごとに1行）+ セーブファイル読み込み + ウィザードの調整。

**adjust ウィンドウがない理由**: 種族には adjust があったが、これは追加される数値ではない。**ゲーム中にキャラクターの体重は変わらない** — 食事でも荷物でも呪いでも。**キャラクターは太らない**。

#### 8つの呼び出し元

1. 持ち運び限界（`inven_ops.c`）
2. 盾 bash の命中とダメージ（`player_melee.c`、2回、1回の呼び出しに折りたたみ）
3. ドア bash（`terrain_commands.c`）
4. キャラクターシート（`char_screen.c`）
5. ダンプファイル（`files.c`）
6. セーブファイル書き込み（`save.c`）
7. ウィザードプロンプト（`wizard.c`）

#### このモジュールが答えないこと

1. **持ち運び限界の計算**: `inven_ops.c` が `use_stat[A_STR] * PLAYER_WEIGHT_CAP + weight` を計算（3000上限）。主語はstrengthで、体重は小さい項。1箇所のみなので折りたたまない
2. **bash の強さ**: `py_bash()`（`/ 10`, `/ 60 + 3`）と `bash()`（`/ 2`）。3つの異なる除数＝3つの異なるルール。bash についての事実であり、body についてではない
3. **表示方法**: `char_screen.c` は `prt_num()` へ、`files.c` は `fprintf("%6d")` へ。種族の名前とは異なり、**2箇所に共通式がない**

### Armour Class

このキャラクターの実際のACはいくつか？ 単位はAC、**大きいほど当たりにくい**。すべてのリーダーは `test_hit()` への引数として、または blow を削るパーセント風の量として使う。26箇所から読まれる。

#### 2つのフィールド、1つの質問

分割は **由来による** もので、意味による分割ではない：
- **ARMOUR HALF**: 装備の `ac` の合計 + 呪文による一時的なポイント（invulnerability 100、blessing 2）
- **MAGICAL HALF**: プラス値：dexterityボーナス（`toac_adj()`）+ 装備の `toac` の合計

**どのリーダーも半分を見ない。** 26箇所すべてが `pac + ptoac` を読むため、分割は使用者には不可視。半分を区別できるのは、構築する4箇所とセーブファイルの2つのshortのみ。

証明：`create.c` は種族選択時と職業選択時で **dexterityボーナスを異なる半分に入れる**（種族時はarmour halfへ、職業時はmagical halfへ）— しかしゲーム内では区別不可能。両方とも同じ合計になるから。

#### 誰が聞くか

モンスター。26のリーダーのうち21は `monster_melee.c` のモンスターの攻撃テスト、4つは `traps.c`（罠のダーツ、投げられたもの）、最後の1つは `monster_melee.c` の `damage -= (ac * damage) / 200`（プレートアーマーがダメージを減らす理由）。

#### セーブファイルとシート

シートは **別の質問**（`player_display_numbers.h`）。`prt_pac()` は `player_display_ac()` を表示し、この数値ではない。2つは意図的に食い違いを許される — 未鑑定の鎧はキャラクターを守るが、シートにはまだ何も表示されない。

### Attack Bonuses (to-hit / to-damage)

すべての命中試行に加算されるもの、すべての着弾した打撃に加算されるもの。2つの小さな数値、典型的には-6〜+9。strengthとdexterityのテーブルから来て（`stats.c` の `tohit_adj()` と `todam_adj()`）、装備・武器で増減する。**負は普通**：弱いか不器用なキャラクターは-3から始まり、呪われた武器はさらに引く。

#### 2つの数値、両方とも答え

**どのリーダーも合算しない**。リーダーは常に狙っているか傷つけているかを知っている：

- **AIM**: キャラクターシートで `BTH_PLUS_ADJ` 倍され、振りの命中ロールに丸ごと加算され、投げの命中ロールにも丸ごと加算
- **FORCE**: すでに着弾した blow のダメージに加算。弓は決してこれを得ない：矢のダメージは矢から来る

#### なぜ1つのモジュールで2つではないか？

**書き込み側が決して分離しないから。** 書き込む4箇所すべてが両方を設定する、隣接する2行で：作成時2回（推測と実値）、`player_bonuses.c` の再計算、セーブファイルの隣接する2つのshort。書き込み方を共有する2つの質問は、2つの答えを持つ1つの質問。

#### 誰が聞くか

キャラクターシートの2つのレーティング（`abilities.c`）、振り（`player_melee.c`、狙いと力で各1回）、投げ（`throw.c`、狙いのみ）、装備カウント中にシートが表示するコピー（`player_display_numbers.c`）、セーブファイル。

#### 表示されるプラス値は別の質問

すでに専用モジュールがある：`player_display_numbers.c` がシートに表示されるものを保持する。これはキャラクターが **知っている** アイテムのみをカウントする。これら2つの数値は実際のもので、すべてをカウントする。

### Base To-Hit

武器・レベル・腕の力を数える前に、このキャラクターは物を殴るのがどれくらい上手か？ 単位は `test_hit()` がターゲットのACと比較するもので、**大きいほど当たりやすい**。ゲーム自身が認める範囲は0〜200（`wizard.c` がその範囲を尋ねる）。ヒューマンウォリアーは振り70・射撃55から始まり、ヒューマンメイジは振り34・射撃20。**負は可能で現実的**：エルフの種族ベースは振り-5・射撃+15なので、エルフメイジは29から始まる。

#### 2つの数値、両方とも答え

- **MELEE NUMBER**: キャラクターが装備品を振るときに使用
- **BOWS NUMBER**: 何かを発射または投げるときに使用。ゲームはこちらにより強く依存 — `throw.c` がすべての種類のランチャーでこれを選ぶ

#### Armour Classの鏡像

そこでは、2つのフィールドが1つの答えを保持：すべてのリーダーが合算し、どのリーダーも半分を欲しがらなかった。ここでは、**どのリーダーも合算しない** — リーダーは常に2つのうちどちらが欲しいかを知っている。blow か shot かをすでに知っているから。

#### なぜ1つのモジュールで2つではないか？

**書き込み側が決して分離しないから。** 書き込む8箇所すべてがペアで行い、8ペアのうち6ペアは両方の数値に **同じ量** を渡す：heroismは各12、super heroismは各24、blessingは各5。種族は両方を与え、職業は両方に加算し、セーブファイルは両方を運び、ウィザード画面だけがゲーム内で片方だけを変更する唯一の呼び出し元。変更方法を共有する2つの質問は、2つの答えを持つ1つの質問。

#### 誰が聞くか

命中ロールが作られる4箇所。振りの `player_melee.c`（2回、明かりのないターゲットは当たりにくいため）、ショットまたは投げの `throw.c`（7回、ランチャーごとに1回）、キャラクターシートの2つのレーティングの `abilities.c`、セーブファイル。

### Display Numbers (shown on sheet)

**これらは戦闘で使われる数値ではない。** 本物のプラス値は：aim と force は `player_attack_bonuses.c` に、ACの2つの半分は `player_armour_class.c` に。この質問はキャラクターに何が伝えられるかのみ。4つのことが違いを現実にし、4つすべてがコピーを実数からの導出にできない理由：

1. **キャラクターの知識でフィルターされる。** `calc_bonuses()` はすべての装備のプラス値を実数に加えるが、アイテムが identified（known2_p）のときのみここに加える。未鑑定のアイテムはベースACを表示する — 呪われていない限り、その場合は保留される

2. **1つのペナルティはここにのみ存在。** 装備するには重すぎる武器は *表示される* to-hitにコスト（`use_stat[A_STR] * 15 - weight`）を課し、他は何もない。実際のaimは決してそれを運ばない（`player_to_hit_bonus`）、攻撃コードが別々に取り除くから（`attack_blows()`, `hit_rolls.c`）。だから表示されるto-hitはフィルターされた実数ではない — 独自に組み立てられる

3. **ACは2回表示され、異なる方法で合算される。** 実数はarmour（pac）とbonus（ptoac）を分ける。シートは "+ To AC" *と* "Total AC" を印刷するため、可視ボーナスは可視合計に折りたたまれなければならない（`player_display_fold_to_ac`）

4. **記憶され、再計算されない。** 4つすべてがセーブファイルに入り、出てくる。途中で `calc_bonuses()` は呼ばれない。復元されたキャラクターが見るシートは保存されたもの。`player_light.c` の明かりの円と同様、これは導出ではなく数値を置く場所のまま

本資料は、プレイヤーの状態（condition）、スキル（skills）、呪文（spells）を管理する3つのモジュール群の設計思想と実装上の注意点をまとめたものである。

## 1. プレイヤー状態（Player Condition）

`player_condition.h` は以下の9つのサブシステムを統合している：

1. ステータスフラグ（status flags）
2. 時限効果（timed effects）
3. 食料（food）
4. 休息（resting）
5. 走行（running）
6. 光源（light）
7. 光る手（glowing hands）
8. 保留中のテレポート（pending teleport）
9. 位置（position）

### 1.1 ステータスフラグ（Status Flags）

**基本構造**：30ビットのワード1つ。セーブファイルのフォーマットそのもの。ビット配置は変更不可。

**4つの用途に分類される**：

1. **効果発動のマーク（14ビット）**：12個はタイマーと対応（英雄、混乱、毒など）、2個は空腹状態と対応。「効果が開始され、告知済み」を示す。`player_note_effect_started()` は新規かどうかを返す。

2. **再計算・再描画の要求（12ビット）**：数値が変わった側が要求を立てて去る。`app/dungeon.c` の1箇所がターン毎に処理。6個は能力値ビット（隣接配置が必須）。要求の扱いは統一されていない：速度、AC、HP、マナ、能力値は `player_take_*_request()` で読取と同時にクリアされるが、腕力チェックと学習行は読取と消去が別。

3. **行動モード（2ビット）**：探索と休息。タイマーなし。移動、再生、速度表示、状態行など多数の箇所から参照される。`PY_SEARCH` は30ビット中で最多の参照回数（9回）。

4. **状態行の記録（2ビット）**：麻痺と繰り返し。画面の現在表示内容を記録し、毎ターン再描画を避けるため。

**このモジュールが意図的に含めないもの**：
- カウントダウン処理（family 1の効果開始時の処理は呼び出し側固有）
- 描画処理（`prt_*()` 群は読取のみここで行う）
- 要求が何を意味するかの判断


### 1.2 時限効果（Timed Effects）

**基本構造**：18個の一時的な状態、それぞれが残りターン数を保持。キャラクターが持つ唯一のクロック。

**ステータスフラグとの関係**：2つは対だが分離されている理由：
- マークはセーブファイル形式の1ワード内のビット
- カウンターは18個のshort
- `breath()` で証明される違い：マークを問う（まだ発動していないカウンター追加があり得る）

**12回繰り返されるスケルトンの畳み込み**：
```c
if (f_ptr->hero > 0) {
    if (player_note_effect_started(PLAYER_EFFECT_HERO)) { ...開始時処理... }
    f_ptr->hero--;
    if (f_ptr->hero == 0) { player_note_effect_ended(...); ...終了時処理... }
}
```
このパターンは `player_timed_in_force()` + `player_timed_beginning()` + `player_timed_count_down()` に畳まれる。各効果の具体的処理（メッセージ、HP、命中、AC、再描画、照明など）は呼び出し側に残る。

**2つのウィンドウに分離する理由**：1ターン残りで開始された効果は、同じターン内で開始と終了の両方が発生する。単一の「開始/継続中/終了」値では表現不可。

**マイナス値の許容**：`app/dungeon.c` は恐怖を打ち消す際にゼロを設定し、同じターンのカウントダウンで-1になる。「== 0」判定を逃すため終了処理がスキップされ、マークも立たない。次の恐怖は1ターン短くなる（`monster_melee.c` は既存値に加算するため）。`player_timed_count_down()` は無条件減算でこの挙動を維持。

**6個はマークなし**：麻痺、幻覚、悪からの保護、2つの耐性、帰還の言葉。告知すべき開始がなく、これらの呼び出し側は開始処理を持たない。

**意図的に含めないもの**：
- マーク（`player_status_flags.c` が所有、このモジュールは設定・消去を依頼するのみ）
- 開始・終了に伴う処理（メッセージ、画面、HP、AC変化、`change_speed()` 呼び出し、`creatures()` 再実行、毒ダメージ）
- 18個中3つの非タイマーフィールド（`rest` は行動モード、`speed` と `see_infra` はクロックが動かす現在値）


### 1.3 食料（Food）

**2つの数値**：満腹度のカウンターと、1ターン毎の消費レート。

**内蔵される2つのルール**（各1箇所の読み手しかなく、胃に関することのみ）：
- 1ターンの消化量 = レートをカウンターから減算（`player_digest`）
- 最初の一口は飢餓の借金を許す：負のカウンターは食料追加前に空にリセット（`player_gain_food`、旧 `add_food()` の先頭）

**意図的に含めないもの**（理由が胃の外にあるため）：
- 閾値判定（`PLAYER_FOOD_ALERT` / `WEAK` / `FAINT` とゼロ）：再生レート選択、`PY_HUNGRY` / `PY_WEAK` 設定、表示。すべて `app/dungeon.c`
- `PLAYER_FOOD_MAX` 超過のペナルティ（`food_ops.c` が速度低下と表示を担当）
- 飢餓ダメージ（ダメージシステムの責務、`app/dungeon.c`）
- 復活キャラの負カウンター解除（`save.c`）
- 嘔吐による150への減少（`potions.c`）

### 1.4 休息（Resting）

**問い**：休息中か、あと何ターンか。

**18個のタイマーとの3つの違い**：

1. **両方向からゼロへ移動**：正の値は「この回数休む」（カウントダウン）、負の値は「HPとマナが満タンになるまで休む」（カウントアップ）。`rest_command.c` は `*` 入力で `-MAX_SHORT` を設定。

2. **2つの終了条件**：ゼロに達する、または（負の場合）HPとマナが両方満タン。後者は2つの別の問いを読むため、呼び出し側（`app/dungeon.c`）に残る。

3. **休息と無関係な読み手**：`creature.c` が3回問う。高速キャラは休息中1ターンに1回しか動かない、眠っているモンスターは休息中に起きにくい、そして `abs(rest) % MON_MULT_ADJ` は繁殖モンスターのペースを刻むクロック。最後は休息と無関係で、単にターン毎に変化する数が欲しいだけ。

**マークは別の場所**：`player_status_flags.c` が `PY_REST` を保持。2つは同時に設定・消去されるが、畳み込みはない（たった2箇所、両方 `rest_command.c` 内）。畳み込むと2行節約できるが、`prt_state()` の順序、消化、「休息を止めるには何かキーを押して」メッセージの順序を押しつけることになる。マークは独自の呼び出し側を保持。`status_line.c` の状態行はマークを問う（プレイ中は一致するが、セーブファイル読込は別々に復元）。

**意図的に含めないもの**：
- `-MAX_SHORT` とプレイヤー入力の検証（`rest_command.c` が担当）
- 開始・停止に伴う処理（状態行、メッセージ、先に止める探索モード、加速・減速する消化）
- HPとマナの満タン判定（2つの別の問い）


### 1.5 走行（Running）

**問い**：プレイヤーは走行中か。

**走行中の挙動変化**（走行と無関係な複数箇所）：
- `@` が描画されない（`map_view.c`）
- ランプの光が正方形毎に塗られない（`lighting.c`）
- すぐ隣のモンスターは暗闇でも気づく（`creature.c`）
- 通行不能の道と足元の物体は無言で通過（`player_move.c`）
- メインループはキー入力を10秒待たずに中断を確認（`app/dungeon.c`）

**歩数カウンター**：存在理由は1つだけ：開けた場所での無限ループ防止のため100歩で切断（`keep_running`）。旧グローバル変数は1つのintで両方の仕事（ゼロ=非走行、それ以外=これまでの歩数）。2つの問いはここで分離され、数値はモジュール内に隠蔽。

**停止は完全ではない**：`end_find()` と `disturb()` は走行を止めるが、それが全てではない。`end_find()` は `move_light()` も呼び、`disturb()` は `check_view()` を呼ぶ。両方とも実際に走行中だった場合のみ実行。この部分は呼び出し側に残る（2つの経路は異なり、差異は画面に関するもので走行に関するものではない）。

**レベル開始時の `forget_run()`**：`app/dungeon.c` のセットアップで、`begin_level()` と `forget_pending_teleport()` の隣。「停止」ではない（走行を途中で切るのではない、画面作業も続かない）ため別ウィンドウ。

**`keep_running()` は停止しない**：このモジュールはカウントのみ。停止は呼び出し側の仕事（旧来通り）。`find_run()` は偽が返ると「息を整えるために走るのをやめた」と表示して `end_find()` を呼ぶ。

### 1.6 光源（Light）

**2つの真偽値** - 純粋なストレージ（`progress.h` や `score_death.h` と同様）。

**`player_has_light()`**：キャラクターは光源を持っているか。
- 装備スロットの光源から導出されない（導出すると遷移が見えない）
- メインループ（`app/dungeon.c`）が毎ターン再計算し、遷移が重要：消灯時は「光が消えた！」表示、キャラクター妨害、レベル全体の照明再計算。点灯時は逆。
- ループ開始前にもスロットから設定（最初のターンを遷移と数えないため）

**`player_light_is_drawn()`**：その光の輝きが現在マップ上に配置されているか（`cave[][].tl` ビットの輪）。
- 上記とは別の問い。同じ `move_light()` 内で並んで読まれるが、異なる。
- 2つの乖離：走行中は `find_prself` オフで光は配置されない（画面のちらつき防止）、失明直後は消すべき前ターンの光がまだマップ上にある。
- 書込も読取も `move_light()` の両半分と `find_init()` のみ。導出する価値がない（答えは「画面がどう見えていたか」で、他の誰も知らない）。

### 1.7 光る手（Glowing Hands）

**問い**：手は光っているか。タイマーなし。

**動作**：巻物11が点灯、1発の攻撃が着地するまで持続（休息、歩行、階段下り、すべてOK）。着地後は消灯（モンスターが混乱したかに関わらず）。

**チャージ**：ゲームは常に1のみ保存。全ての呼び出し側は真偽値として扱う。int型なのはセーブファイルがbyteを保持するため（`player_glowing_hands_restore()` 参照）。

**光っている間に2枚目の巻物**：何も起こらない（巻物の識別もされない）。呼び出し側は先に `player_glowing_hands()` を確認。

**名前の由来**：`confuse_monster(dir, row, col)` は `spells.c` の関数で、杖や巻物が今1体のモンスターに行うこと。これは今キャラクターが持っている何か。ゲームのメッセージも手を名指し（「手が光り始めた」「手が光らなくなった」）。

**意図的に含めないもの**：
- 2つのメッセージ（`msg_print()` は `externs.h` の向こう、このモジュールは含まない）
- モンスターが混乱するか（レベル判定、`m_ptr->confused` への加算、思い出の記録。すべてモンスターに関するもの）
- どの攻撃だったか（`monster_melee.c` は `adesc != 99` も確認。攻撃の種類に関すること）
- 巻物が識別されるか（`scrolls.c` は手が暗かった場合のみ `ident` 設定。巻物のルール）


### 1.8 保留中のテレポート（Pending Teleport）

**1ビット**：存在理由は1つの罠のため。

**なぜ存在するか**：他のすべてのテレポートはその場で `teleport()` を呼ぶ。テレポート罠（`traps.c`）は移動の途中で踏まれる可能性があり、プレイヤーを今いる場所で先に照らす必要がある - 「テレポート罠を照らしてから、テレポートする」。そのため罠は記録を残し、メインループ（`app/dungeon.c`）がターンのコマンド終了後に読み取り、`teleport(100)` を呼ぶ。

**`teleport_done()` の呼び出し**：`teleport()` （`player_move.c`）が出口で呼ぶ。すべてのテレポートに対して呼ばれる（予約された種類だけではない）。他の原因からのテレポートも罠が残した記録を消す。旧来の挙動で無害（プレイヤーは移動済み、記録が求めていたこと）。

**`forget_pending_teleport()` vs `teleport_done()`**：レベル開始時に `app/dungeon.c` が `begin_level()` の隣で呼ぶ。「それが起こった」ではない（テレポートは実行されない）ため、`teleport_done()` とは別ウィンドウ。

### 1.9 位置（Position）

**純粋なストレージ**（`progress.h` と同様）。範囲チェックなし、どの正方形が合法かも知らない（旧コードがどちらも行わなかったため。ここで行うと挙動変更になる）。

**ゲッター名**：プレイヤー名で命名（このファイル名ではない）。284回読まれ、ほぼ常に既に何をしているか言っている式の内部（`cave[player_row()][player_col()]`、`los(player_row(), player_col(), y, x)`）。`player_pos_row()` は各箇所でノイズを追加するだけ。読み取りでないエントリポイントはモジュール接頭辞を保持（読み手が「誰がプレイヤーを動かすか」を名前で見つけられるように）。

**`player_place(int row, int col)`**：プレイヤーをどこかに置く。1歩踏む呼び出し側もレベルをテレポートする呼び出し側も、ここを通る。行と列は常に一緒に設定される（片方だけ変更した呼び出し側は一度もない）。

パラメータがintなのは全ての呼び出し側がint座標を持っているため。int16_tへの縮小はここで起こる（5箇所の代入サイトではなく）。同じ縮小をこれらの代入は既に行っていた。

**`player_pos_forget()`**：プレイヤーがどこにいたかを忘れる。新レベル生成時に、プレイヤーをどこに置くか決める前に行う（`generate.c`）。-1（どのレベル上にもない行と列）を書く。-1は読み戻されない（位置を-1やゼロと比較する呼び出し側はない）。これはリセットであり、何かがテストする「どこにもいない」状態ではない。


## 2. プレイヤースキル（Player Skills）

`player_skills.h` は6つの能力値を統合：

1. 罠解除（disarm）
2. 隠密（stealth）
3. セービングスロー（saving throw）
4. 探索（search skill）
5. 赤外視野（infra-vision range）
6. 速度（speed）

### 2.1 罠解除（Disarm）

**問い**：知能、レベル、クラスを数える前の、罠分解と鍵開けの上手さ。単位はパーセンテージ的確率（罠の難易度を引いた後に `randint(100)` と比較）。大きいほど成功しやすい。人間戦士は約25、ハーフリング盗賊は約60で開始。ウィザード画面は0〜200を認める。

**1つの数値、2つの用途**：罠と鍵は同じスキル。`traps.c` は罠と箱に、`terrain_commands.c` は施錠扉と閉じた箱に使う。片方だけ欲しがった呼び出し側は一度もない。

**開始値の出所**（2つのテーブル、両方作成時）：
- 種族が基礎を与える（`race_type.b_dis`）：人間0、ハーフエルフ2、エルフ5、ノーム10、ハーフリング15など。小柄な種族が優れる。
- クラスが加算（`class_type.mdis`）：聖騎士20、戦士25、僧侶25、魔法使い30、レンジャー30、盗賊45。

**器用さボーナスは一度焼き込まれる**：`create.c` は `race[i].b_dis + todis_adj()` を保存。作成時の器用さボーナスの1コピーがこの数値内に凍結され、全ての読み手は現在のボーナスの2コピーを上に追加。後でポーションが器用さを変えると、2つの現在コピーは動くが凍結コピーは動かない。ゲームが常にそうしてきた挙動。このモジュールは数値を保持し、ルールを整理しない。

**呼び出し側**：鍵や罠を扱う3箇所（`terrain_commands.c` 2回、`traps.c` 1回）、キャラクターシート、ウィザード画面、セーブファイル。

**畳み込まれていない合計**：4箇所が綴る
```c
disarm + 2 * todis_adj() + stat_adj(A_INT)
        + class_level_adj[pclass][CLA_DISARM] * player_level() / 3
```
最後の文字まで同一（`abilities.c`、`terrain_commands.c` 2回、`traps.c`）。4つを1ウィンドウに畳むのは可能だが、`player_disarm.c` が `player_class.c` を呼ぶことになる（それ自体が1つの単位）。

**意図的に含めないもの**：
- 実際にロールされる合計（上記の式）
- 試みが成功するか（`(i - t_ptr->p1) > randint(100)` は呼び出し側、罠の難易度も）
- 盲目、混乱、幻覚（`traps.c` は合計を10で割る）

### 2.2 隠密（Stealth）

**問い**：眠っている何かの横をどれだけ静かに歩くか。単位はパーセンテージでも確率でもなく、半減の回数。使用箇所は
```c
notice = randint(1024);
if (notice * notice * notice <= (1L << (29 - stl))) { ...眠っている者が目を覚ます }
```
1ポイント毎に気づかれる確率が半減。大きいほど静か。最も粗い数値：罠解除は0〜200、これは-1〜18、1ポイントがその範囲全体に相当する価値。

**範囲の出所**：
- 種族が基礎（`race_type.stl`）：ハーフリング+4、ノーム+3、ハーフエルフとエルフ+1、人間0、ドワーフとハーフオーク-1、ハーフトロル-2。小柄は静か、大柄はうるさい。8種族中3つが負。
- クラスが加算（`class_type.mstl`）：盗賊+5、レンジャー+3、魔法使いと僧侶+2、戦士と聖騎士+1。全クラスが何か加算。最低は-1（ハーフトロル戦士）、最高は9（ハーフリング盗賊）。
- 装備が加算・返却（`TR_STEALTH`）：3スロット、各1〜3ポイント：ディフェンダー武器、隠密のブーツ、隠密のマント（`item_enchant.c` で各 `t_ptr->p1 = randint(3)`）。作成時の9に装備の9で、ウィザード画面の「-1-18」の由来。**プロンプトは到達可能な範囲をそのまま認める**（他のプロンプトは0-200と言って近づけもしない）。

**シフトには必要十分な余地**：見た目はオーバーフローを待っているようだが。下端で `1L << (29 - -1)` は `1L << 30`、つまり1,073,741,824。1024の3乗も1,073,741,824。よって-1のキャラクターは常に気づかれ、3乗はシフトが作れる最大数を越えない。上端では `1L << 11` は2048、よって1〜12のロールのみ起こす（12の3乗は1728、13の3乗は2197）：1024中12回の確率。もう1歩下がると `1L << 31`（符号付きlongで未定義）だが、何もその一歩を踏めない：2つのテーブルは-1未満に合計できず、ゲーム内のアイテムは隠密を下げない（うるさい呪いは代わりに `TR_AGGRAVATE` を設定）。このモジュールは数値をそのまま保持、検証は責務外。


### 2.3 セービングスロー（Saving Throw）

**問い**：知恵、レベル、クラスを数える前の、呪文・罠・呪いへの抵抗力。単位はパーセンテージ的確率（`randint(100)` と比較）。大きいほど振り払いやすい。ハーフリング戦士は36、人間戦士は18、ハーフトロル戦士（クラステーブルが許す種族の最悪ペア）は10で開始。

**開始値の出所**（2つのテーブル、両方作成時、何も焼き込まない）：
- 種族が基礎（`race_type.bsav`）：人間0、ハーフオーク-3、ハーフトロル-8、ハーフエルフ3、エルフ6、ドワーフ9、ノーム12、ハーフリング18。負は実際の答え（罠解除と同様）。
- クラスが加算（`class_type.msav`）：戦士18、聖騎士24、僧侶30、盗賊30、レンジャー30、魔法使い36。呪文使いが最も抵抗する。

**1つの数値、2つの評価値に変換**（キャラクターシート）：
- 「セービングスロー」：`stat_adj(A_WIS)` と `CLA_SAVE` 列を加算
- 「魔法デバイス」：`stat_adj(A_INT)` と `CLA_DEVICE` 列を加算

杖や魔法棒の扱いはこの同じ数値を、知恵の代わりに知能で読む。`tests/put_misc3_test.c` は書かれた時からこれを疑わしいと呼ぶ（デバイスは罠解除に自然に紐付く）。意図されたかは知りようがなく、ゲームの挙動なので保持される。このモジュールは数値のみ保持、どちらの評価値も計算しない。

**名前に注意**：`save` はこのソースツリーで最も混雑した語。`src/app/save.c` と `save_char()` はゲーム書出、`save_screen()` は表示、`device_use_chance()` の第1パラメータはまさにこの数値、`direction.c` はローカル `int save` でコマンド回数を保持、`race_type.bsav`、`class_type.msav`、`CLA_SAVE`、`player_abilities.save` は近隣の4つの綴り。`grep -w save` は `src/*.c` で83行を見つける。11行がこの問い。

**`player_saves()` に注意**：その関数（`player_damage.c`）はロールそのもの。「今回抵抗したか」を真偽値で答える。このウィンドウは「どれだけ抵抗がうまいか」を数値で答える。ロールはそこに留まる（`randint()` と `class_level_adj[pclass]` も必要）。

**ウィザード画面の矛盾**：プロンプトは「(0-100)」と言い、続く検査は0〜200を認める。罠解除のプロンプトと同じ検査、上の文が違う。このウィンドウはどちらにせよ何も拒まない。

### 2.4 探索スキル（Search Skill）

**問い**：隠れた扉や罠を探す時、成功する確率は - そして求められずに探索が起こる頻度は。2つの小さな数値、両方とも種族テーブルとクラステーブルから、その後装備で動く。

**2つの数値、両方が答え**：基礎命中（`player_base_to_hit.h`）や攻撃ボーナス（`player_attack_bonuses.h`）と同じ形。AC（全ての読み手が加算する2つのフィールドで1つの答え）の反対。ここでは組み合わせる読み手なし。2つは1箇所で隣り合う（`player_move.c`、再び `terrain_commands.c`）。そこでさえ別のことを聞かれる：頻度は探すかどうかを決定、確率は探索が何か見つけるかを決定。

- **確率**：`search()` に直接渡される。大きいほど良い。
- **頻度**：1/nの確率。`randint(n)` が1になると探索が起こる。小さいほど良い。キャラクターシートは上下逆転（`40 - frequency`）して評価値として読めるようにする。

**なぜ1モジュールで2つでないか**：2つはほぼ常に一緒に動く。クラステーブルは両方に加算、探索装備は両方を動かす - 反対方向、同じ量。ゲーム全体で1箇所の書き手のみが片方だけ触る（デバッグエディタ）。

**呼び出し側**：探索モード自身のターン（`app/dungeon.c`）、走行中の自動探索（`player_move.c`）、休息やトンネル掘り中の自動探索（`terrain_commands.c`）、キャラクターシートの2評価値（`abilities.c`、上下逆転の計算がある場所）、デバッグエディタ（`wizard.c`）、セーブファイル。

**「今探索中か」とは別の問い**：それはフラグで、既にウィンドウがある（`player_is_searching()` は `player_status_flags.h`）。`search_on()` / `search_off()` が切り替え。このモジュールは探索の上手さを保持、起こっているかではない。だからファイルは `player_searching.c` と呼ばれない。

**2つのsetterウィンドウ**（ペアでない、攻撃ボーナスと違い）：1箇所の書き手が片方だけ設定するため。`wizard.c` は金、次に探索、次に隠密と歩く。頻度は聞かない。作成の2つも3行離れている（基礎命中のウィンドウが間に座る）。何もペアとして書かれない。

**1つのペアadjustウィンドウ**（setterと違い）：呼び出し側は片方だけ加算しない。2つの量は別パラメータであり1つでない（呼び出し側が符号を所有）。`py_bonuses()` は `(amount, -amount)` を渡し、作成は `(msrh, mfos)` を渡す。このウィンドウ自身が第2量を否定すると、作成は `(msrh, -mfos)` を書く必要が生じる。


### 2.5 赤外視野（Infra-vision Range）

**問い**：温血生物をどれだけ遠くで見分けられるか。単位は正方形（1正方形=10フィート）。ゼロは赤外視野なし（人間の開始位置）。

**なぜ「range」で「vision」でないか**：`PLAYER_TIMED_INFRA_VISION` （`player_timed_effects.h`）はポーションのクロック、ターン単位でカウント。これはこの数値を動かす3つのものの1つ。これを `player_infra_vision()` と命名すると、そのクロックから1文字離れ、真偽値（「赤外視野を持っているか」）と読まれかねない。実際は距離。

**3つのものがここに数値を置く**（ウィンドウの形の理由）：
- **種族**、1回、キャラクター作成時（`create.c`）：人間0、ハーフエルフ2、エルフ3、ハーフリング4、ノーム4、ドワーフ5、ハーフオーク3。**開始値は常にゼロではない**、だから下記の決定ウィンドウはセーブファイル読み手だけでなく2つの呼び出し側を持つ。
- **装備**、アイテムの価値分（`player_bonuses.c`）：`py_bonuses()` は装着時にfactor 1、外す時に-1で呼ばれる。1行で両方向をカバー。
- **ポーション**、続く間ちょうど1正方形（`app/dungeon.c`、クロック開始のターンと尽きるターンの両方で）。

**意図的に含めないもの**：
- クロック：ポーションのターンは `player_timed_effects.c` に属し、押上げは `app/dungeon.c` に留まる（既にクロックの開始や尽きを知っているファイル）。クロックとこの数値は1つの事実の2つの半分ではない。この数値は3つの源を持ち、クロックはその1つ。
- 特定のモンスターが現れるか：`creature.c` は「範囲内か かつ 温血か（`CD_INFRA`）」を聞く。後半はモンスターに関すること。前半をここに畳むと半分の問いを閉じ、`> 0` ガードの整理を招く（実際は冗長 - モンスターはプレイヤー自身の正方形に置かれない、距離は少なくとも1 - が除去しない、挙動変更になるため）。
- フィート：キャラクターシートは10倍して「%d feet」と書く（`abilities.c`）。それは数値の見せ方で、何であるかではない。
- 限界：ゲームは範囲に対してこの数値を検査しない、ウィンドウも同様（マナ、HP、速度と同じルール）。

### 2.6 速度（Speed）

**問い**：通常速度から何歩離れているか。ゼロが通常。18個のクロックの1つではなく、ターン数でもない：何もこれをカチカチ動かさない。ポーション、アイテム、罠が来たり去ったりする間、加算・減算される。

**符号は名前が示唆するものと逆**：正は遅い。`prt_speed()` （`status_line.c`）は1で「遅い」、それ以上で「非常に遅い」、0で空白、-1で「速い」、それ以下で「非常に速い」を表示。加速ポーションは `change_speed(-1)` を呼び、`TR_SPEED` アイテムは `change_speed(-amount)` を呼び、鈍化ポーションは `change_speed(1)` を呼ぶ。符号を間違えると速いと遅いが入れ替わる。テストは両端から方向を釘付けにする。

**意図的に含めないもの**：
- モンスター：`change_speed()` （`player_bonuses.c`）はレベル上の全モンスターの `cspeed` に同じ数値を加算、`monster_place.c` はモンスター配置時に `cspeed` に混ぜる。これはエンジンの「減速したプレイヤーは代わりにモンスターを速く動かして扱う」（`creature.c`）言い方。ループと合計は呼び出し側に留まる。このモジュールはプレイヤーの数値のみ保持。
- 食料：加速したキャラクターは余分な食料を燃やす、歩数の2乗（`app/dungeon.c`）。2乗することが速度を飢えに変える方法で、それは別の問い（`player_food.c`）。
- 探索モードの1歩：状態行は探索中1歩を減算（2回、`prt_speed()` と `prt_stat_block()` で）。探索はステータスワードのfamily 3、別の問い。これの別の半分ではない。速度は探索中かどうかに関わらず同じことを意味する。
- 荷物：`burden.c` は荷物が何歩コストをかけているか覚える（`check_strength()` は `change_speed()` に差分を渡すため - 新歩数から覚えている歩数を引く）。合計はここに住む。荷物が答えられる部分はあちらに住む。
- 限界：ゲームは範囲に対してこの数値を検査しない、ウィンドウも同様（マナとHPと同じルール）。


## 3. プレイヤー呪文（Player Spells）

`player_spells.h` は2つのサブシステムを統合：

1. 既知呪文（spells known）
2. 学習可能数（spells to learn）

### 3.1 既知呪文（Spells Known）

**純粋なストレージ**（`progress.h`、`score_death.h`、`hp_table.h`、`player_light.h`、`burden.h` と同様）。何も導出されない：キャラクターが学んだことは歴史で、知る唯一の方法は記録しておくこと。

**4つのデータ構造**（1つの問いに一緒に答える）：
- 学習済みビットフィールド（31呪文上）
- 動作済みビットフィールド
- 忘却済みビットフィールド
- 学習順リスト（32呪文番号）

`calc_spells()` （`spellbook.c`）はキャラクターのレベル変化に応じて学習済みと忘却済みの間で呪文を移動。`gain_spells()` は学習済みリストに追加。`magic.c` / `prayer.c` は動作済みとマーク。

**ビット演算（`1L << spell`）はこちら側**：呼び出し側は呪文を番号で聞く（それが持っているもの：`magic_spell[]` と `spell_names[]` へのインデックス）。`SPELL_NONE` でシフトすると未定義なので、そのケースもこちら側で処理（`spells_known.c`）。

**`SPELL_NONE` = 99**：学習順（`spell_order`）の「まだ呪文なし」を表す値。ゲーム開始時にこれで埋められ（`app/main.c`）、そのままセーブファイルに書かれる。変更不可。

**主要なウィンドウ**：

- **`spell_is_learned(spell)`**：今キャストできる呪文。レベルを超えた呪文は `calc_spells()` でここから移動（忘却済みへ）。学習・思い出しで戻る。`SPELL_NONE` は偽を返す（呼び出し側がマーカーを先に確認せずに学習順を歩けるように）。

- **`spell_is_forgotten(spell)`**：知っていたがレベルや能力値変化で失った呪文。呪文リストで「forgotten」表示（`spellbook.c`）。

- **`spell_has_worked(spell)`**：呪文が一度成功裏にキャストされた。最初の成功は経験値（`magic.c`、`prayer.c`）、これが2回払いを止める。それまで呪文リストは「untried」表示。

- **`spell_learn(spell)`**：初めて呪文を学ぶ：既知とマークし、学習順に追加。2つは常に一緒（`gain_spells()` が2回行った、選択呪文と授与祈祷で各1回）。一緒に保つことが順序の使用可能性を保証。

- **`spell_forget(spell)` / `spell_remember(spell)`**：既知と忘却済みの間で移動。学習順はそのまま（`calc_spells()` がどの呪文を最初に返すか知る方法）。

- **`spell_learned_nth(n)`**：n番目に学んだ呪文（0が最初）、またはまだそんなに学んでいなければ `SPELL_NONE`。忘れた呪文も順序に留まる（これは歴史、キャスト可能リストではない）。

**セット照合**：
- **`spells_learned_among(spells)`**：与えられたセット内でキャラクターが知っている呪文。セットは呪文書から来る（`inven_type.flags` は呪文毎1ビット保持）。「この本の中でどの呪文をキャストできるか」に答える（`spellbook.c`）。

- **`spells_not_learned_among(spells)`**：与えられたセット内でまだ知らない呪文 - 学習の候補（`spellbook.c` 2回：魔法使いは本から、僧侶は全呪文から）。

**セーブファイル**：3つのビットフィールドと学習順を生の表現で渡す（`save.c`）。ファイル形式は固定：3ワード、次に32バイト、この順序。

### 3.2 学習可能数（Spells to Learn）

**名前**：カウントであり、呪文のリストではない。どの呪文が既知かは別の場所（`spells_known.h`）。

**問い**：今あと何個呪文を学べるか。`calc_spells()` はキャラクターのクラス、レベル、能力値が許す数を計算し、既に知っているものを引き、残りをここに保存。`gain_spells()` が勉学を求められた時、1呪文ずつ消費。

**チャージ**（光る手と同様、`player_glowing_hands.h`）：1個以上あり得る。光る手と違い、キャラクターがレベルを得る度に再計算される。`calc_spells()` は上げる、下げる、ゼロにする可能性がある（能力値低下で呪文を忘れる時）。

**意図的に含めないもの**：

1. **いくつ許されるか**：`calc_spells()` の9方向テーブルがクラステーブル、能力値、レベルを読む。1つの呼び出し側、1箇所。

2. **どの呪文が既知か**：それは `spells_known.h`。`calc_spells()` は `learned_spell_count()` を引いてこの数を作るが、2つは1つの事実の半分ではない：このカウントは記憶される（セーブファイルに入っている）、`gain_spells()` が消費、既知呪文から読む度に再計算されない。

3. **不足している本**：`gain_spells()` は手元の本が含むより多くの呪文を許される可能性がある。学べるものを学び、差分を戻す。「この本にどの呪文が入っているか」は本の責務。

4. **3つのメッセージ**：「新しい%sを学べる」「新しい%sを学べない！」「本が不足しているようだ」は `msg_print()` に属する（`externs.h` の向こう、このモジュールは含まない）。

5. **状態行の再描画**：`PY_STUDY` は既に自身の問い（`player_status_flags.h`）。2つは一緒に動くが、画面の再描画が必要かは表示に関すること、カウントに関することではない。

---

## まとめ

この3つのモジュール群は、元々グローバル変数や `player_type` 構造体に散在していた状態を、問いに基づいて整理したもの。各モジュールは：

- **単一の問いに答える**（またはごく近い問いのグループ）
- **セーブファイル形式を保持**（ビット配置、フィールド順序）
- **派生可能でも記憶が必要な情報**（遷移の検出、歴史の保存）
- **意図的に含めないものを明示**（責務の境界）
